# PLAN — multi-IDE notifications (codex / cursor / windsurf)

> **Status: the Claude half shipped 2026-10-16; codex / cursor / windsurf not started.** Blocked on: none of the three agents is installed on the dev machine, so every hook below has to be written and reviewed blind, then validated on a machine that has the agent.
> Context: `PLAN - multi-IDE-v1.md` (session lifecycle per provider), `REPORT - multi-IDE feasibility.md` (per-agent hook surfaces).

## Context

AirPrompt itself never produces a notification for a session. Every agent has its own notification hook wired into its own config (`~/.claude/settings.json` → `notify.sh` for Claude), and that hook POSTs an enriched payload to the daemon's `/api/notify`; `public/notify.js` only renders what arrives. AirPrompt's provider adapters wire **no notification event today** — their `hookEvents` maps carry `sessionStart` / `stop` only (plus Claude's `statusLine`, which the plugin manifest cannot declare) — so Claude is the only agent that notifies at all, and that through a user-owned script living in the `~/.claude` repo, not here.

What a notification carries is therefore decided in the agent's hook, not in the daemon or the UI. The fields the web UI and the desktop popup both read: `session_label`, `subtitle`, `turn_info`, plus `notification_type` / `message` / `permission_mode` / `effort`.

Since 2026-10-16 `turn_info` is `"<turn duration> — <context tokens>"` (e.g. `4.0s — 125k`), with the token badge read by `src/hooks/airprompt-session-tokens.js` — provider-agnostic, one reader per agent, and **nothing printed** when the provider's session log has no such record. The old `N msgs` counter was dropped: it was noise, and it did not exist for any agent other than Claude anyway.

## Goal

Every supported agent posts the same payload shape to `/api/notify`, so the web UI and the phone show one kind of notification regardless of which agent is driving the session, with the context-token badge wherever the agent's session data exposes it — and silently without the badge where it does not.

## Per-agent work

### Codex

- **Event:** `Notification` exists in Codex's hook system (`REPORT - multi-IDE feasibility.md:83`), and Codex passes hook context as **snake_case** JSON on stdin (`codex.js:136`). Wire it the same way the existing lifecycle hooks are wired (`install-common.js` `hookCommand` + the `SessionStart`/`Stop` entries in `codex.js:235-239`).
- **Token source:** `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` → `event_msg` / `payload.type === "token_count"` / `payload.info.last_token_usage.input_tokens` — the prompt that request re-sent, i.e. the context; `total_tokens` (which adds that request's output) is read only when `input_tokens` is absent, and the cumulative `total_token_usage` never is. The reader is written and unit-tested against that documented shape, but has never seen a real rollout.
- **Blind risks:** the `Notification` matcher values, the stdin field names (snake_case? `session_id` vs `session-id`), and how a hook is expected to find _its own_ rollout file. If the payload carries no session/path field, resolving the rollout by session id (matching `session_meta` inside each rollout) is guesswork until someone runs `AIRPROMPT_DEBUG=1` against a real install and dumps the stdin.

### Cursor

- **Event:** Cursor's documented events include `sessionStart`, `sessionEnd`, `stop`, `beforeSubmitPrompt`, `afterAgentResponse`, `afterAgentThought`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `preCompact`, `workspaceOpen`. **There is no `sessionIdle`** in the docs — the feasibility report's mention of it needs to be treated as unverified. The closest fit for "the agent finished a turn and is idle" is `stop` (which, unlike `sessionStart`, carries `conversation_id` but **not** `session_id`).
- **Token source:** `afterAgentResponse` carries `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`; `preCompact` carries `context_tokens` / `context_usage_percent` / `context_window_size`. So Cursor does not need a log parser at all — the hook can pass the number straight through with `--tokens <n>`, which the reader already supports (and which is the only path that works for a provider whose on-disk transcript format we have not verified).
- **Blind risks:** whether `stop` is the right event for a completion notice, whether `transcript_path` (documented, may be `null`) is worth reading, and whether firing on `afterAgentResponse` (once per response) is too chatty — the notification policy has to be decided here, not later.

### Windsurf

- **Event:** our adapter knows two (`on-open` at `windsurf.js:76-80`, `post_cascade_response` wired at `windsurf.js:181`), and `post_cascade_response` is the only plausible completion signal — Windsurf's documented event set is wider (`PLAN - multi-IDE-v1.md:204`), so the pair is a statement about our adapter, not about what exists. Its stdin shape is the least documented of the three — `windsurf.js:95` already parses it "tolerantly" for that reason.
- **Token source:** none known. Expect the badge to be omitted; `--tokens` is available if a payload field ever turns out to carry one.
- **Blind risks:** everything about its payload. Whatever is written must fail open and print nothing rather than a wrong badge.

## Design decisions to lock before writing code

1. **Where the hook lives.** One shared notification script in the repo (`src/hooks/`) that every provider's `hooks.json` points at, taking the provider id and reading that agent's stdin shape — versus one template per provider. The lifecycle hooks already solved this with `core/` + thin per-provider wrappers; a notification hook should follow the same split, otherwise the payload enrichment gets written three times.
2. **What it does.** POST to `/api/notify` only (web UI + phone), with the desktop popup left to whatever the user already runs — or own the desktop popup too. The daemon's only `notify-send` today is the pairing popup (`server.js:105-118`), on the auth path, not on the notification path, so taking on session popups is new scope.
3. **Notification policy.** Which event is "done" for each agent, and whether permission prompts (`permission_prompt`) are representable at all in agents that have no such event. A hook that fires on every response is worse than no notification.
4. **Payload parity.** Same field names as the Claude payload (`session_label`, `subtitle`, `turn_info`, `notification_type`, `message`, `permission_mode`, `effort`) so the UI needs no per-provider branch. `turn_info` stays the agent's own formatted string; the UI never parses it.
5. **Unknown-tokens contract.** No badge, never a made-up number (already enforced by `airprompt-session-tokens.js` returning empty).

## Verification without the agents installed

- **Unit-testable now:** the reader (already covered in `test/unit/session-tokens.test.js`) and stdin parsing, using recorded stdin fixtures. Fixtures must be **synthetic but documented**, marked as such in the test — a fixture invented from docs and then asserted against is a tautology, so each fixture needs a note saying where its shape came from and that it is unverified.
- **Testable with a local harness:** point the provider's `configDir()` at a temp dir, write the `hooks.json` entry, run the hook with synthetic stdin, assert the POST body against a stub `127.0.0.1` listener (the same trick `notification-test/send.sh` uses). This proves wiring and payload shape, not the real agent's stdin.
- **Only verifiable on a real install:** the event names, the matchers, the stdin field names, and whether the token source exists at all. The first real run should be done with `AIRPROMPT_DEBUG=1` and the raw stdin captured, then the fixture in the test replaced with the real one.

## Open questions

- Does Codex's `Notification` hook fire for the same semantics as Claude's `idle_prompt`, or does it need a different trigger (e.g. a `Stop`-equivalent hook plus a timer)?
- Does Cursor's `stop` fire per turn or only when the conversation is closed?
- Should the web UI distinguish an agent that has no token source from one whose count is momentarily unknown? Today both render as "no badge".
- Is per-provider notification support wanted at all for Windsurf, given the payload is undocumented and it has no session-end hook?
